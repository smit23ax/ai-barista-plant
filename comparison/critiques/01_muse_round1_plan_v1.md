2. Is stlite on GitHub Pages a good choice?
Yes as a goal, no as an untested commitment. It matches the course's recommended pattern — a standalone WebAssembly build on GitHub Pages — and it preserves the real app instead of rebuilding it in JavaScript. The course example, though, is not a stlite app: it is Rust compiled to WebAssembly doing the computation, with a Python/numpy/scipy reference. That is lightweight and fast. A full stlite app is the opposite end of that spectrum.
Risks, checked:

* Load time and phone performance. Stlite downloads Pyodide plus wheels — the original stlite notes put that at ~50 MB including the runtime and some packages — and “a large amount of resources will be downloaded” on first open. Other guides warn it “will take a minute to load”, code runs 3–20x slower, and phones give “significantly poorer performance”. Your Streamlit Cloud app already takes ~30 seconds cold. In class, on a phone, this could be a blank screen while you talk.
* Version mismatch is the likely first failure. Your pins are very new. Stlite dictates the Streamlit version — “You can control the versions of `stlite` (which also dictates the Streamlit version)” — and Pyodide's bundled package versions lag PyPI. The plan's “facts to check” list is right to flag this, but it should be step 0, not a build step. Do not assume `streamlit==1.66.0`, `pandas==3.0.5`, or `scikit-learn==1.9.1` exist in the Pyodide/stlite combination you pick.
* The CoolProp premise is wrong. The plan says swap CoolProp because it is “not available in the browser.” CoolProp's own docs say Pyodide “includes many of the scientific Python packages, including NumPy, SciPy, and CoolProp”, that it has been bundled since Pyodide 0.24.0, and that from CoolProp 8.1.0 WebAssembly wheels are provided on PyPI. Test CoolProp in stlite first. Swapping it for a polynomial or table introduces a new physics error source, forces recalibration, and invalidates the 0.1% test the plan proposes — which is a good test, but for the wrong decision.
* Most of the stack is plausibly fine, but “plausibly” is not a test. Pyodide maintains ports including “NumPy, SciPy, pandas, Polars, scikit-learn”, and Plotly is a pure-Python install via micropip. The unknowns are the exact versions, `scipy.integrate.solve_ivp`, `scipy.optimize.least_squares`, the GP optimizer with `n_restarts_optimizer=2`, `st.segmented_control`, `st.plotly_chart`, file downloads, and your `data/*.json` and overlay PNGs being mounted in the browser filesystem. Pint is a red herring: in your repo it is only used in `plant/standards.py` for test-time unit checks, not in the runtime physics, so guard or strip that import in the browser build instead of letting it block the demo.
* State does not persist. Lab notebook batches live in session state. In stlite that evaporates on reload, and there is no server to save to. The plan does not address seeded example batches, export, or what a visitor sees on first open — currently, an empty notebook.

Alternatives, in order I would actually consider them:

* A: Ship the stlite demo, but make Streamlit Cloud the primary demo link and add a lightweight static fallback. A pure HTML/JS grind-size explorer using the same Ergun numbers, precomputed in Python, gives the professor something instant if WASM fails. This is the safest for grading.
* B: Ship a lite stlite demo only. Port just the Packed bed / grind explorer, not the GP optimizer, calibration, and all 8 views. Faster, fewer dependencies, and it matches the professor's framing.
* C: Follow the course example more literally. Keep the full app on Streamlit Cloud, and build a small Rust/JS or Python-to-WASM Ergun calculator for Pages. More work, best performance, but a second codebase to keep consistent.
* D: Do not do what the plan implies — do not rebuild the docs in a new KaTeX pipeline. You already have `docs/derivations.html` at 792 KB, server-rendered KaTeX, offline, no CDN, via `docs/render_katex.js` and `scripts/build_guide.py`, with KaTeX 0.16.22. Reuse that build. The plan's “pre-rendered by KaTeX at build time” is correct, but it reads as if you are starting from scratch.

3. Is the two-model comparison fair and convincing?
No, as designed. Three problems:

* Opus 5.5 vs Sonnet 5.5 is not a convincing “different AI models” test. Same provider, same model family, likely correlated strengths and failures. Requirement 5 says “different AI models” and “at least 2 different AI models.” A professor can reasonably read that as expecting cross-provider independence. Make the second model non-Anthropic — ChatGPT or Gemini — as the primary second, not “if I run it myself.” Keep Sonnet as a third if you want, but do not let it be the comparison.
* The task is too small and too cosmetic. Building the “How it was made” page plus an Ergun-chart widget tests HTML/CSS and chart styling, not the hard parts: Ergun physics, dimensional analysis, WASM porting, or the GP optimizer. A model can win that task and still be wrong on physics. The comparison should test what the course grades.
* The criteria reward the wrong things. “Lines of code” rewards verbosity. “Time taken” depends on your prompting, network, and iteration style. “Number of corrections needed” depends on who is correcting and how strict they are. “Renders on laptop and phone without overlap” is binary and necessary, but not discriminating. Only “equations correct and every symbol defined with SI units” and “numbers match the tested Python model” are strong — and they need tolerances and hidden tests to be meaningful.

How to fix it: freeze one prompt, one starting snapshot, one iteration budget, and one pre-registered test suite before either model starts. Give both models the same meaningful task — for example, implement the channeling unit or the grind-size explorer as a standalone, testable piece, with the existing `pytest` physics tests as the pass bar. Score blind if you can, keep both outputs in the repo with diffs, and state why the winner ships in numbers, not impressions. Also be explicit on the comparison page that this critique itself is from a different model — Muse — and that the plan was Opus 5.5, so the critique/comparison trail is already cross-model, even before implementation.
4. What would make the “AI process” page convincing to a fluids professor who likes AI?
Evidence, agency, and failure — in that order. A timeline v1→v5 is not evidence if the files are not in the repo. Right now v1 and v2 do not exist as files, and v3–v5 exist only as sections in `progress.txt`. A professor who clicks “every claim links to a plan file or a commit” will find broken links.
Make it convincing by showing: the exact prompt, date, model version, and what changed in the diff; what you rejected and why — the PINN idea as too familiar to your professor, coffee as the everyday topic, trimming scope, recentring on packed-bed framing; what the AI got wrong with numbers before/after — the Moroney drip-filter misreading, Ergun constants not fitting real coffee beds; and what you checked yourself — the Corrochano 1.9–16x over-prediction, the Re_p range, the calibration fit. Your standards are already strong: every symbol defined with SI units, automated tests for physics, units, and KaTeX. Show the test output, not just the claim. And name the AI's limits in your own words: where it extrapolated, where you bounded Δp at 0–8 bar for display, where the model cannot close the TDS gap.

Keep the core, but do not let the plan's “Course content” page become a dump of the Theory view.

* Missing and must be added: a one-page validity map — Re_p range, ε, bed length/diameter, grind distribution vs single-sphere assumption, bed consolidation, and where Ergun breaks down at fine grind. * Missing: material and energy balances as first-class content, not “links.” The app has them in Trends — kettle 22.5 kJ, losses 8.4 kJ, 63% efficiency — but the plan does not say where they live on the site.
* Missing: an assumptions and bounding box. The live app says “Carman–Kozeny overestimates plunging pressure, and Ergun blows up at fine grind — bounded 0–8 bar for display.” That bounding is a display choice, not physics. Say so, with the unbounded numbers alongside.
* Weak: channeling. Two parallel Darcy paths is a nice idea, but the plan gives it equal weight to Ergun with no validation data named. Label it as illustrative / hypothesis, or cut it from the graded course-content page and keep it as an extension.

Keep them in the demo, do not give them equal space on the documentation pages.
